02

What was actually tested

This site is a single-owner CMS (one admin, no client sign-in, no payments on-site — purchases happen on Amazon). Whole sections of a generic QA template don't apply here; rather than pad the report with them, they're listed once in §07. What follows is real findings from live testing and source review, not a checklist filled in by assumption.

03

High priority

Admin login has no rate limitingHigh

Where: app/api/admin/login/route.ts — confirmed by code review; no rate-limit or lockout logic exists anywhere in the project.

Why it matters: the passcode is the single gate protecting the entire admin — every board and product, and by extension everything shown on the public site. Nothing currently stops unlimited automated guesses against it.

Recommended fix: add a simple per-IP limiter (e.g. 5 attempts / 15 min) in front of the login route — Vercel KV or Upstash Redis both work well on Vercel's free tier. The sibling Digitale project already has this exact pattern on its chat endpoint; it can be ported directly.

04

Medium priority

Sessions can't be individually revokedMedium

Where: lib/admin-auth.ts — the session cookie is a constant HMAC of a fixed string, not a per-login token.

Why it matters: if a session cookie is ever copied off a device, there's no way to invalidate just that copy — logout only deletes the cookie in the browser that clicks it. The only true revocation is rotating ADMIN_SESSION_SECRET, which also logs out the real owner.

Recommended fix: acceptable as-is for a single-owner site; worth revisiting only if the admin is ever used from a shared or public device.

No custom 404 or error pageMedium

Where: confirmed live at /products/nonexistent-slug-xyz — correct 404 status, but Next.js's bare default page (no header, no branding, no link back into the site).

Recommended fix: add app/not-found.tsx styled with the site's own header/footer, so a mistyped or stale link doesn't dead-end.

No baseline security headersMedium

Where: next.config.ts — no headers() configured.

Why it matters: no X-Frame-Options/frame-ancestors means the admin passcode page could be embedded in an invisible iframe on another site (clickjacking); no baseline CSP either.

Recommended fix: add a headers() block: X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, and a basic CSP once the deployed origin is known.

No robots.txt or sitemapMedium

Not a bug, but worth having before real traffic — Next.js supports both as simple route files (app/robots.ts, app/sitemap.ts).

05

Low & informational

Leftover test products still liveLow

test, test101, test 102, TEST carousel-in-new-product, and Auto-Edit Flow Test Product are still in the database — one is hidden, the rest are still publicly visible on the Cropped Jacket board. Hide or delete before launch.

Link fields accept any string, including javascript:Info

Buy/reviews/video URL fields only show a soft "doesn't look valid" warning — they never block saving. Since only the trusted owner can set these, this is self-XSS at most, not externally exploitable.

Uploaded file type is trusted from the browser, not sniffedInfo

Image/video type checks read the browser-reported MIME type, not the file's actual bytes. Low practical risk here since the allowed set is limited to safe raster/video formats — no SVG, no HTML.

06

What held up well

Confirmed by live testing against the running app, not just reading the code.

Every admin API route rejects unauthenticated requests — verified livePass

Called GET/POST/DELETE on the products and boards APIs with the session cookie stripped out: all four returned 401. Enforced server-side in each route, not just hidden in the UI.

Stored XSS attempt rendered as inert text — verified livePass

Created a real product with <script>window.__xss_fired=true</script><img src=x onerror=...> in its name, description, and notes, then loaded its public page. The payload appeared as plain visible text — neither script fired. No dangerouslySetInnerHTML exists anywhere in the codebase. Test product deleted afterward.

Service-role key never reaches the browserPass

Every file touching SUPABASE_SERVICE_ROLE_KEY is guarded with import "server-only". No Supabase anon key is used anywhere, so there's no direct client-to-database path to probe at all.

Cookie flags and passcode comparison are correctPass

httpOnly, secure in production, sameSite: lax — confirmed live that JavaScript cannot read or overwrite the cookie. Passcode comparison uses timingSafeEqual, resistant to timing attacks.

Draft/scheduled content is genuinely hidden from the public sitePass

Both public queries (board page, product page) filter on publish_at; a direct link to a draft or not-yet-scheduled product returns a real 404, not a preview.

No secrets committed to gitPass

.env.local is gitignored with no history of ever being committed; .env.example holds only placeholders.

Mobile layout holds upPass

Checked a product page at 375px: no horizontal scroll, sticky "Shop this" bar and affiliate disclosure both render correctly.

09

Method

Testing combined source review (auth, API routes, upload validation, git history) with live testing against the running local build: unauthenticated API calls, a real stored-XSS attempt (created and deleted as test data), a bad-slug 404, and a 375px mobile pass. No destructive actions were taken, no real user data exists on this single-owner site, and no load/stress/brute-force testing was performed.
